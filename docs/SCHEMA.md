# 성공습관 데이터 모델 — 스키마 변경 결정 기록

> **AI는 임의로 저장 파일의 키 추가·이름·뜻 변경, 옛 형식 읽기 코드 수정을 하지 않는다**(CLAUDE.md '스키마 변경 게이트').
> 스키마 변경 절차: ① 변경안을 이 문서 '변경 이력'에 먼저 기록 → ② 사용자 확인 → ③ 코드 반영
> → ④ **구버전 저장본을 실제로 읽어 옛 파일 읽기 실측 + 되돌리기 경로(옛 APK 덮어 설치) 확인 + 사용자 실테스트**
> 후 배포 (일반 트랙 검증 갈래, CLAUDE.md '검증 강도'). 새 코드로 만든 빈 저장소는 통과하고 옛 저장소만 깨진다.
> 이 문서는 "결정과 이유"를, 코드는 "현재 상태"를 담당한다. 항목 목록을 손으로 이중 관리하지 않는다.

> **상태: 확정(2026-11-19 사용자 확인).** 이후 변경은 위 절차를 따른다.
> 2026-11-21에 채록에서 갈라지며 수집물·대화·외울 문장·설정 절을 뺐다(그 설계는 M채록 저장소 `chaerok_phone`의 `docs/SCHEMA.md`). **계획 저장 형식은 그때 한 글자도 바뀌지 않았다**(그 뒤 옛 파일이 그대로 읽히는 키 추가는 아래 변경 이력).

## 설계 원칙
1. **저장소는 파일 나무 하나다.** 데이터베이스를 쓰지 않는다. 앱 전용 폴더(`filesDir`) 아래에 파일로 둔다.
2. **백업·내보내기·기기 옮기기 수단이 없다**(사용자 결정 2026-11-19). 앱을 지우거나 폰을 잃으면 데이터가 사라진다.
3. **사용자 데이터와 산출물을 다른 자리에 둔다.** 산출물(로그·위젯 요약)은 지워도 된다.
4. **사용자 데이터 쓰기는 임시 파일에 쓰고 이름 바꾸기**(`atomic_file.dart`). 쓰는 곳은 `file_writers_test` 등록부로 고정한다.
   예외: 로그는 직접 덧붙인다 — 깨져도 되는 산출물이다.

## 핵심 엔티티와 관계
- **계획·하루 평가** = 파일 2개. 다른 것과 관계 없음.

## 도메인별 설계 결정

### 폰 안의 폴더 나무
```
filesDir/
  plans/plans.json, reviews.json   ← 사용자 데이터. 계획·하루 평가
  chaerok.log, chaerok.log.1       ← 산출물(로그)
  widget/today.json                ← 산출물(F-102 홈 화면 위젯 요약 — 계획에서 다시 만든다, 지워도 된다)
```
- 갈라지기 전 앱(2026-11-19~21 사이의 '성공습관')이 깔려 있던 폰에는 `records/`·`changed.txt`·`sent_clip.md5` 같은 채록 쪽 흔적이 남아 있을 수 있다 —
  이 앱은 읽지도 지우지도 않는다(숨기기 전 APK로 시험 저장한 것이 있을 때만 생긴다).

### 계획 저장 (기존 「채록」 형식 + 옛 파일이 그대로 읽히는 추가만)
- `plans/plans.json`·`plans/reviews.json`. 항목의 뜻은 `docs/requirements/계획.md`의 각 절 '가정'에 있다
  (`held`·`kind`·`weekend`·`weekday`·`holidays`·`released`), 코드는 `app/lib/plans.dart`. 파일 이름은 `app/lib/app_paths.dart`(`app_paths_test`가 고정).
- **결정**(2026-11-27 문구 정정): **옛 파일이 그대로 읽히는 추가만 한다** — 새 키는 없으면 옛 동작으로 읽고, 기존 키의 이름·뜻은 바꾸지 않는다.
  `weekend` 키가 없는 이력 칸(기존 채록의 나누기 전 형식)도 읽는다. 더한 키는 아래 '변경 이력'에 있다(여기에 키 목록을 다시 적지 않는다),
  새 키도 그 절차(기록 → 사용자 확인)를 거친다.
- **이유**: 사용자 폰에 이 형식으로 쌓인 계획이 있고 백업이 없다 — 옛 파일을 못 읽게 되면 되찾을 수 없다. 키를 더하는 것은 옛 파일을 깨지 않는다.
- 평문이고 앱 전용 폴더 + `allowBackup=false`로 지킨다.
